# Security

## Threat model

The server is designed for **trusted MCP clients operated by trusted users**. Maxima evaluation is
arbitrary code execution by design; a client that can call `maxima_eval` can run any expression the
Maxima language permits.

Deployments that expose the server to untrusted users or networks must treat it as a code-execution
service and isolate it accordingly (container/VM, no credentials, resource limits, network egress
controls).

Primary assets:

1. The host filesystem and processes reachable by Maxima.
2. Secrets in the MCP server's environment.
3. Availability of the server and its Maxima processes.
4. Integrity of documentation/source results shown to the model.

## Safe mode

`MAXIMA_MCP_ALLOW_DANGEROUS=false` (the default) blocks many shell and file-system primitives using
token scanning that ignores string literals and comments. Blocked names include:

`system`, `run`, `batch`, `batchload`, `load`, `save`, `writefile`, `appendfile`, `read`, `openw`,
`opena`, `stringout`, `file_search`, `gnuplot_out_file`, `gnuplot_preamble`, `gnuplot_term`,
`eval_string`, `parse_string`, `to_lisp`, `lisp`, `quit`, `exit`, `texput_file`; plus `:lisp` and
shell-style `!` escapes.

Dedicated tools provide vetted alternatives:

- `maxima_package_load` loads only exact names present in the installed share index.
- `maxima_plot` generates output paths and gnuplot preambles internally.

**Safe mode is defense in depth, not a sandbox.** Maxima is dynamically typed and highly
introspective; determined code can potentially reach dangerous functionality through aliases,
indirect application, package internals or Lisp-level features. Do not rely on safe mode as a
security boundary for hostile input.

## Process isolation

- Each session is a separate `maxima` child process.
- The child receives a **minimal environment**: `PATH`, `HOME`, `TMPDIR`/`TEMP`/`TMP`, locale
  variables and `DISPLAY`. It does **not** receive `MAXIMA_MCP_AUTH_TOKEN` or arbitrary host
  credentials.
- The working directory is a fresh temporary directory per process.
- The Maxima userdir is persistent under the cache directory so compiled package artifacts survive
  restarts. It is writable by the server user.
- On timeout, cancellation, output overflow or crash, the child is terminated with `SIGTERM` and
  then `SIGKILL`.

## HTTP security

- **Bind address**: defaults to `127.0.0.1`. Binding to `0.0.0.0`/`::` is allowed but produces a
  startup warning when no auth token is configured.
- **Authentication**: `MAXIMA_MCP_AUTH_TOKEN` enables Bearer authentication on `/mcp` and
  `/metrics`. Comparison is constant-time.
- **Host validation**: loopback binds accept only loopback `Host` values; `MAXIMA_MCP_ALLOWED_HOSTS`
  restricts hosts for other deployments. This mitigates DNS-rebinding attacks.
- **CORS**: `MAXIMA_MCP_CORS_ORIGINS` defaults to `*`; set explicit origins in production.
- **Rate limiting**: fixed-window per source IP, default 120 requests/minute. Disable with
  `MAXIMA_MCP_RATE_LIMIT=0` only behind a trusted rate-limiting proxy.
- **Body limit**: default 2 MB. Expression length and command count are independently limited.
- **Session ids**: random UUIDs generated by the SDK. Session ids are routing identifiers, not
  capabilities; every request still requires the bearer token when configured. Any authenticated
  client can address a known session id, so do not share tokens across tenants.

Health endpoints (`/healthz`, `/readyz`) are intentionally unauthenticated but expose only coarse
status. `/` exposes name/version. `/metrics` requires the token when one is configured.

## Resource exhaustion

| Control                       | Default          |
| ----------------------------- | ---------------- |
| Evaluation timeout            | 30 s (max 300 s) |
| Session count                 | 8 processes      |
| Idle session expiry           | 15 min           |
| Retained output per statement | 200,000 chars    |
| Raw output buffer             | 1,000,000 bytes  |
| Per-process memory (RSS)      | disabled (0)     |
| Expression length             | 100,000 chars    |
| Commands per batch            | 50               |
| Plot image size               | 10 MB            |
| HTTP body                     | 2 MB             |
| HTTP rate limit               | 120/min          |

Timeouts kill the process rather than interrupting a computation cooperatively; this prevents a
single pathological expression from blocking a session indefinitely. When
`MAXIMA_MCP_MAX_MEMORY_MB` is set, the child's resident set size is sampled on Linux and the process
is killed if it exceeds the ceiling, bounding memory in addition to wall-clock time.

### OS-level confinement (optional)

Environment minimization and safe mode are not a sandbox. For deployments that accept untrusted
input, add an operating-system confinement layer around the Maxima child:

- **Docker**: the shipped `docker-compose.yml` already runs the container `read_only`, drops all
  capabilities, disables `new-privileges`, and uses a tmpfs `/tmp`. Docker's default seccomp profile
  additionally blocks `ptrace`, `mount`, `keyctl`, and other privileged syscalls. A stricter custom
  profile can be applied with `security_opt: ["seccomp=/path/to/profile.json"]` and should block
  network namespace creation and further filesystem syscalls if the workload permits.
- **Landlock**: on kernels ≥ 5.13, wrap the child with a Landlock profile that restricts filesystem
  access to the configured cache and source directories. This is the strongest filesystem boundary
  available in pure userspace.
- **rlimits**: `docker run --memory=... --pids-limit=...` (or `ulimit -v` for a non-container
  deployment) bounds the whole container/process; `MAXIMA_MCP_MAX_MEMORY_MB` bounds each Maxima
  child specifically.

None of these layers should be treated as a substitute for running untrusted tenants in separate
containers/VMs.

## Filesystem and source access

- Documentation and source tools read only from configured directories.
- `maxima_doc_read` accepts a single `.html` basename and validates it against the section index.
- Source reads resolve paths and require them to be inside `MAXIMA_MCP_SRC_DIR` or
  `MAXIMA_MCP_SHARE_DIR`.
- `maxima_package_load` requires an exact package name from the share index; path separators and
  traversal are rejected.
- Plot output is written to a fresh temporary directory and deleted after reading.

## Logging and secrets

- Logs go to stderr in JSON (or pretty) format.
- Authorization headers and token-like fields are redacted; configuration is not logged wholesale.
- Tool arguments are not logged by default; only failures log tool name, error code and message.
- Maxima's minimal child environment prevents `getenv` leakage of server secrets.

## Multi-tenant guidance

The server is not a multi-tenant sandbox. For multiple untrusted tenants:

1. Run one container/VM per tenant.
2. Do not inject cloud credentials or host mounts.
3. Use a read-only root filesystem where possible, plus a writable cache volume.
4. Apply CPU and memory limits; Maxima can consume large amounts of both.
5. Restrict network egress unless package downloads are required.
6. Set `MAXIMA_MCP_ALLOW_DANGEROUS=false`, explicit CORS origins and a strong auth token.
7. Put TLS and additional authentication/authorization in front of the HTTP transport.

## Reporting a vulnerability

Please do not open a public issue for security problems. Report privately to the maintainers with:

- affected version/commit,
- reproduction steps or proof of concept,
- impact assessment,
- suggested mitigation if known.

You should receive an acknowledgement within a few business days. We will coordinate a fix and
disclosure timeline with you.
